# Migrating from fabric-dataops-toolkits 2.x to Sigantry 3.0

Status: Authoritative for the 2.x -> 3.0 upgrade. It was referenced from every DeprecationWarning emitted by the v3.0 shim packages; those shims were dropped in v3.1, so on v3.1+ the legacy names fail outright rather than warning.

> **Distribution name, if you are installing today:** this page documents the historical
> 2.x -> 3.0 rename, when the plan was to publish the base package as `sigantry-core`.
> The open-source release publishes it as **`sigantry`** (`pip install sigantry`), and
> `sigantry-core` does not resolve on PyPI. The import package `sigantry_core` is
> unchanged. See [ADR-0017](../decisions/ADR-0017-distribution-name-sigantry.md).
Licence note: v3.0 is Apache-2.0 (see [ADR-0010](../decisions/ADR-0010-commercial-model.md)). v2.x was proprietary. If you were distributing v2.x artefacts under closed terms, v3.0 changes the licence; review ADR-0010 before upgrading.

## TL;DR

1. `pip install sigantry-core` (and `sigantry-hs2` if you use the HS2 plugin). The legacy `fabric-dataops-toolkits` and `fabric-dataops-toolkits-hs2` wheels installed during v3.0 as deprecation shims and **dropped in v3.1**.
2. Rename imports: `fabric_dataops_toolkits` -> `sigantry_core`. Rename `fabric_dataops_toolkits_hs2` -> `sigantry_hs2`.
3. Config file: rename `.fabric-dataops.toml` to `.sigantry.toml`. The loader now resolves `.sigantry.toml` by default and reads the old filename for one more minor release with a `DeprecationWarning`. Explicit config paths work with any filename.
4. Env vars: both operational variables and the typed-settings loader now use the `SIGANTRY_*` prefix. Settings overrides are `SIGANTRY_<SECTION>__<KEY>`; the legacy `FDT_` prefix is read for one more minor release with a `DeprecationWarning`.
5. Rename CLI invocations: `fabric-dataops-toolkits doctor` -> `sigantry doctor`.
6. PowerShell: `Import-Module Fabric` -> `Import-Module Sigantry`. Function names unchanged.

If you do nothing, your v2.x code keeps running on v3.0 through the shims -- with `DeprecationWarning` messages pointing at this guide on every import. **The shims dropped in v3.1**: from v3.1 the legacy dist names no longer install and the legacy import paths fail. Migrate the imports (axis 1) before upgrading past 3.0.x.

## Why this change

See [PRODUCT-BRIEF.md](../PRODUCT-BRIEF.md) for the productisation rationale and [ADR-0011](../decisions/ADR-0011-rename-to-sigantry.md) for the rename-cutover decision record.

The shims that point you here emit one of three deprecation warnings on first import. Each warning text is reproduced verbatim below so you can grep your CI logs and find this guide:

- Python base: `fabric-dataops-toolkits has been renamed to sigantry-core in v3.0. This shim re-exports sigantry-core under the legacy name and drops in Sigantry v3.1. Migrate now: replace 'pip install fabric-dataops-toolkits' with 'pip install sigantry-core' and rewrite 'from fabric_dataops_toolkits ...' imports as 'from sigantry_core ...'. See docs/migration/2.x-to-3.0.md.`
- Python HS2 plugin: `fabric-dataops-toolkits-hs2 has been renamed to sigantry-hs2 in v3.0. This shim re-exports sigantry-hs2 under the legacy name and drops in Sigantry v3.1. Migrate now: replace 'pip install fabric-dataops-toolkits-hs2' with 'pip install sigantry-hs2' and rewrite 'from fabric_dataops_toolkits_hs2 ...' imports as 'from sigantry_hs2 ...'. See docs/migration/2.x-to-3.0.md.`
- PowerShell: `The Fabric PowerShell module is renamed to Sigantry. This shim drops in Sigantry v3.1. Migrate: Import-Module Fabric -> Import-Module Sigantry. See docs/migration/2.x-to-3.0.md.`

## Migration axis 1 -- Python imports

Sed recipe (Linux / macOS / WSL — run from the root of your consumer repo, inside a git branch):

```bash
find . -type f \( -name "*.py" -o -name "*.ipynb" \) -not -path "*/.git/*" \
  -exec sed -i 's/fabric_dataops_toolkits_hs2/sigantry_hs2/g' {} +
find . -type f \( -name "*.py" -o -name "*.ipynb" \) -not -path "*/.git/*" \
  -exec sed -i 's/fabric_dataops_toolkits/sigantry_core/g' {} +
```

PowerShell equivalent (Windows, run from the root of your consumer repo, inside a git branch):

```powershell
Get-ChildItem -Recurse -Include *.py, *.ipynb |
  Where-Object { $_.FullName -notmatch '\\.git\\' } |
  ForEach-Object {
    (Get-Content -Raw -LiteralPath $_.FullName) `
      -replace 'fabric_dataops_toolkits_hs2', 'sigantry_hs2' `
      -replace 'fabric_dataops_toolkits',     'sigantry_core' |
      Set-Content -NoNewline -LiteralPath $_.FullName
  }
```

Order matters: the HS2 plugin substring (`fabric_dataops_toolkits_hs2`) is a superset of the base substring (`fabric_dataops_toolkits`) so the plugin pattern MUST be replaced first, otherwise the second pass partially rewrites already-renamed identifiers to `sigantry_core_hs2`.

Run your test suite after each pass. On the v3.0 line the shim accepted old imports, so a partial migration was safe there; on v3.1+ it is not — finish both passes before you upgrade past 3.0.x.

## Migration axis 2 -- Config file

Old location: `.fabric-dataops.toml` (repo root).
New location: `.sigantry.toml` (repo root).

```bash
git mv .fabric-dataops.toml .sigantry.toml
```

PowerShell equivalent:

```powershell
git mv .fabric-dataops.toml .sigantry.toml
```

No content changes inside the file are required -- the Sigantry config loader reads the same keys.

`load_settings()` and `FabricDataOps.from_config()` now take no argument by default and resolve the file themselves: `.sigantry.toml` if present, otherwise `.fabric-dataops.toml` with a `DeprecationWarning` naming the rename. The legacy filename is removed one minor release later, so rename now and the warning goes away. Passing an explicit path still overrides resolution entirely and accepts any filename.

## Migration axis 3 -- Environment variables

Old prefix: `FABRIC_DATAOPS_*`.
New prefix: `SIGANTRY_*`.

Audit your CI / shell profiles / K8s configmaps:

```bash
grep -rn "FABRIC_DATAOPS_" .github/ azure-pipelines.yml templates/ .env* 2>/dev/null
```

PowerShell equivalent:

```powershell
Select-String -Path .github\*, azure-pipelines.yml, templates\*, .env* -Pattern 'FABRIC_DATAOPS_' -SimpleMatch
```

For each hit, rename to `SIGANTRY_`. This now covers the typed-settings loader too: `FDT_CORE__TENANT_ID` becomes `SIGANTRY_CORE__TENANT_ID`. The `FDT_` prefix is still read for one more minor release and warns when it is used; where the same setting is supplied under both prefixes, `SIGANTRY_` wins.

Only `SIGANTRY_<SECTION>__<KEY>` forms are read as settings, and `<SECTION>` must name a real settings section (`core`, `auth`, `telemetry`, `release`, `workflow`, ...). Your other `SIGANTRY_*` variables -- `SIGANTRY_SMTP_PASSWORD`, `SIGANTRY_FABRIC_TOKEN` and the rest -- are operational, are deliberately *not* read into the settings object, and are unaffected by this rename.

If you use `.env` / dotenv files, run a sed pass against them too:

```bash
find . -type f \( -name "*.env" -o -name ".env.*" \) -not -path "*/.git/*" \
  -exec sed -i 's/FABRIC_DATAOPS_/SIGANTRY_/g' {} +
```

PowerShell equivalent:

```powershell
Get-ChildItem -Recurse -Include *.env, .env.* |
  Where-Object { $_.FullName -notmatch '\\.git\\' } |
  ForEach-Object {
    (Get-Content -Raw -LiteralPath $_.FullName) `
      -replace 'FABRIC_DATAOPS_', 'SIGANTRY_' |
      Set-Content -NoNewline -LiteralPath $_.FullName
  }
```

## Migration axis 4 -- Entry-point groups

Plugins registered under `fabric_dataops_toolkits.deploy_profiles` (etc.) continue to be discovered — the registry reads both the legacy and the new groups. First-party packages dropped their legacy tables in v3.1; the legacy-group read path remains as a third-party grace window and is scheduled for removal via the LEGACY-SURFACE-DROP roadmap item. When you rev your plugin, update its `pyproject.toml`:

```toml
# BEFORE
[project.entry-points."fabric_dataops_toolkits.deploy_profiles"]
my_profile = "my_plugin.deploy:MyProfile"

# AFTER (required in v3.1+; both names are tolerated during v3.0)
[project.entry-points."sigantry.deploy_profiles"]
my_profile = "my_plugin.deploy:MyProfile"
```

The six canonical seam groups migrate identically: `deploy_profiles`, `dq_gates`, `telemetry_sinks`, `auth_providers`, `runbook_registries`, `capacity_policies`.

If you have many entry-point declarations, the same sed recipe pattern works on `pyproject.toml`:

```bash
sed -i 's/fabric_dataops_toolkits\./sigantry./g' pyproject.toml
```

PowerShell equivalent:

```powershell
(Get-Content -Raw -LiteralPath pyproject.toml) `
  -replace 'fabric_dataops_toolkits\.', 'sigantry.' |
  Set-Content -NoNewline -LiteralPath pyproject.toml
```

## Migration axis 5 -- PowerShell modules

```powershell
# Old
Import-Module Fabric
Import-Module Hs2Fabric

# New
Import-Module Sigantry
Import-Module SigantryHs2
```

The `Fabric` PowerShell module shipped as a deprecation shim during v3.0. It emitted one `Write-Warning` per `Import-Module` call and redirected `Get-FabricToken` / `Get-FabricTenantSetting` through `Sigantry` via a `Set-Alias` indirection. **The shim dropped in v3.1** -- `Import-Module Fabric` no longer resolves; use `Import-Module Sigantry`.

`Get-Hs2FabricToken` and `Get-Hs2FabricTenantSetting` function names are UNCHANGED across the rename; only the module name changes. Existing scripts that call those functions continue to work as long as they `Import-Module SigantryHs2` (or the legacy `Hs2Fabric` shim) at the top.

## Migration axis 6 -- CLI

```bash
# Old
fabric-dataops-toolkits doctor
fabric-dataops-toolkits --help

# New
sigantry doctor
sigantry --help
```

During v3.0, `fabric-dataops-toolkits` was a CLI alias shim pointing at the same `sigantry_core.cli:app`, printing a deprecation notice on first invocation. **The alias dropped in v3.1** -- only `sigantry` resolves.

If you have CI YAML that invokes the CLI by string, the same sed pattern works:

```bash
find .github/ azure-pipelines.yml templates/ -type f -name "*.yml" \
  -exec sed -i 's/fabric-dataops-toolkits /sigantry /g' {} +
```

PowerShell equivalent:

```powershell
Get-ChildItem -Recurse -Path .github, azure-pipelines.yml, templates -Include *.yml |
  ForEach-Object {
    (Get-Content -Raw -LiteralPath $_.FullName) `
      -replace 'fabric-dataops-toolkits ', 'sigantry ' |
      Set-Content -NoNewline -LiteralPath $_.FullName
  }
```

## Verifying the migration

```bash
# Python
pip install sigantry-core==3.0.*
python -c "import sigantry_core; print(sigantry_core.__version__)"   # expect 3.0.0

# CLI
sigantry doctor

# Config + env
test -f .sigantry.toml && echo "config renamed"
env | grep -E '^(FABRIC_DATAOPS|SIGANTRY)_' | sort
```

```powershell
# PowerShell
Import-Module Sigantry -Force
Get-FabricToken -TenantId <your-tenant>
```

If `sigantry doctor` lists your plugins and no `DeprecationWarning` surfaces during a clean run (`python -W error::DeprecationWarning -c "import sigantry_core"` exits 0), migration is complete.

## Staying on v2.x

v3.1 has shipped (and the current line is 3.4.x), so the shim escape hatch is gone. If you cannot migrate yet, pin `sigantry-core<3.1` — that keeps the legacy import paths working via the v3.0 shims without locking you out of v3.0 features. Pinning the legacy dist name is no longer an option.

## Rollback

If v3.0 breaks a workflow, `pip install fabric-dataops-toolkits==2.0.1` on the old name still works (the 2.x wheel remains on the ADO Artifacts feed). Downgrading is always safe; the v3.0 runtime writes nothing to your filesystem that 2.x cannot read.
