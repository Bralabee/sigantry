# Legacy names: from `fabric-dataops-toolkits` to Sigantry

Before the rename recorded in [ADR-0011](../decisions/ADR-0011-rename-to-sigantry.md), Sigantry's code used the working name `fabric-dataops-toolkits`. Sigantry is published on PyPI as **`sigantry`** ([ADR-0017](../decisions/ADR-0017-distribution-name-sigantry.md)), and its import package is `sigantry_core`. A few of the old names are still read, with a `DeprecationWarning`, so existing configuration keeps working while you rename it. This page lists the old names of the import package, the config file, environment variables, entry-point groups and the console script, what replaces each one, and which of them the code still reads.

> **The 1.0.0 release on PyPI reads only the old config names.** Given no path, it looks for `.fabric-dataops.toml`, and it reads settings overrides as `FDT_<SECTION>__<KEY>`. The behaviour described below is that of releases after 1.0.0 and of a source install of `main`. The [README](../../README.md) explains what to do on 1.0.0.

## TL;DR

| Old name | New name | Still read? |
|---|---|---|
| `fabric_dataops_toolkits` (import package) | `sigantry_core` | No |
| `.fabric-dataops.toml` (config file) | `.sigantry.toml` | Yes, with a `DeprecationWarning`; beside a different `.sigantry.toml`, it is the file read, with a `UserWarning` |
| `FDT_<SECTION>__<KEY>` (settings override) | `SIGANTRY_<SECTION>__<KEY>` | Yes, with a `DeprecationWarning`; through 1.0.x it wins over `SIGANTRY_` |
| `FABRIC_DATAOPS_<NAME>` (operational variable) | `SIGANTRY_<NAME>` | No |
| `fabric_dataops_toolkits.<seam>` (entry-point group) | `sigantry.<seam>` | Yes, with a `DeprecationWarning` |
| `fabric-dataops-toolkits` (console script) | `sigantry` | No |

## Python imports

The `fabric_dataops_toolkits` import package is not shipped. Rename the imports in your code, from the root of your repository, on a branch:

```bash
find . -type f \( -name "*.py" -o -name "*.ipynb" \) -not -path "*/.git/*" \
  -exec sed -i \
    -e 's/\bfabric_dataops_toolkits\.\(deploy_profiles\|dq_gates\|telemetry_sinks\|auth_providers\|runbook_registries\|capacity_policies\)\b/sigantry.\1/g' \
    -e 's/\bfabric_dataops_toolkits\b/sigantry_core/g' {} +
```

PowerShell equivalent:

```powershell
Get-ChildItem -Recurse -Include *.py, *.ipynb |
  Where-Object { $_.FullName -notmatch '\\.git\\' } |
  ForEach-Object {
    (Get-Content -Raw -LiteralPath $_.FullName) `
      -replace '\bfabric_dataops_toolkits\.(deploy_profiles|dq_gates|telemetry_sinks|auth_providers|runbook_registries|capacity_policies)\b', 'sigantry.$1' `
      -replace '\bfabric_dataops_toolkits\b', 'sigantry_core' |
      Set-Content -NoNewline -LiteralPath $_.FullName
  }
```

The first pattern turns the six legacy entry-point group names, wherever your code spells them out, into their `sigantry.<seam>` groups (see [Entry-point groups](#entry-point-groups)); the second renames the import package. Both match whole names only, so a plugin package whose name begins `fabric_dataops_toolkits_` is left as it is: rename it to that plugin's new name yourself.

## Config file

Rename the file. Its keys do not change:

```bash
git mv .fabric-dataops.toml .sigantry.toml
```

Called with no path, `load_settings()` and `FabricDataOps.from_config()` read from the working directory (`sigantry sync apply`, `sigantry sync pull` and, when `--expected-group` is not given, `diagnose-auth` call `load_settings()` this way):

1. `.sigantry.toml`, if the legacy file does not exist, or holds the same bytes;
2. otherwise `.fabric-dataops.toml`. On its own it is read with a `DeprecationWarning` naming the rename. Beside a `.sigantry.toml` with different contents it is still the file read, as on 1.0.0, with a `UserWarning` instead: move your settings into `.sigantry.toml` and delete the legacy file to switch;
3. otherwise no file: settings come only from environment variables and defaults.

A path passed explicitly, as in `from_config("my-config.toml")`, is read as given, whatever its name. A `DeprecationWarning` from the settings loader is attributed to the first caller outside sigantry, so Python shows it by default when that caller is the script being run. Otherwise set `PYTHONWARNINGS=default::DeprecationWarning` in the environment, or run Python with `-W default::DeprecationWarning`. `sigantry sync apply` and `sigantry sync pull` record the settings warnings and print none of them, as 1.0.0 printed none, so a pipeline step that fails on any stderr output keeps passing: run the check under [Verify](#verify) to see them.

## Environment variables

Settings overrides take the form `SIGANTRY_<SECTION>__<KEY>`, for example `SIGANTRY_CORE__TENANT_ID`. The legacy `FDT_` prefix is still read and warns when it is used. Through 1.0.x every source 1.0.0 read keeps its 1.0.0 result: where one setting is supplied under both prefixes, the `FDT_` value is used, and a `SIGANTRY_` value overrides `.sigantry.toml` but only fills what the legacy file, or a file passed by path, leaves unset. A `UserWarning` names each `SIGANTRY_` variable that a different legacy value overrides. Unprefixed names that 1.0.0 also read, such as `TENANT_ID` or `PROVIDER`, are not read at all, and a `FutureWarning` names each one that is set. Only variables whose `<SECTION>` names a real settings section (`core`, `auth`, `telemetry`, `release`, `workflow`, ...) are read as settings. Other `SIGANTRY_*` variables, such as `SIGANTRY_SMTP_PASSWORD` or `SIGANTRY_TRUSTED_PLUGIN_DISTS`, are operational: the code that uses them reads them directly, under those names only. Operational variables are not read under the old `FABRIC_DATAOPS_` prefix, and nothing warns when one is set: rename the prefix to `SIGANTRY_`.

## Entry-point groups

The registry still reads the six legacy groups `fabric_dataops_toolkits.deploy_profiles`, `fabric_dataops_toolkits.dq_gates`, `fabric_dataops_toolkits.telemetry_sinks`, `fabric_dataops_toolkits.auth_providers`, `fabric_dataops_toolkits.runbook_registries` and `fabric_dataops_toolkits.capacity_policies`, and files each plugin it finds there under the matching `sigantry.<seam>` group. A plugin registered only under a legacy group triggers a `DeprecationWarning` pointing at this page; each `Registry` warns once per plugin name. If the same plugin name is registered under both groups, the `sigantry.<seam>` entry wins. Rename the tables in your plugin's `pyproject.toml`:

```toml
# BEFORE
[project.entry-points."fabric_dataops_toolkits.deploy_profiles"]
my_profile = "my_plugin.deploy:MyProfile"

# AFTER
[project.entry-points."sigantry.deploy_profiles"]
my_profile = "my_plugin.deploy:MyProfile"
```

```bash
sed -i 's/fabric_dataops_toolkits\./sigantry./g' pyproject.toml
```

## CLI

The console script is `sigantry`, also reachable as `python -m sigantry_core`. There is no `fabric-dataops-toolkits` command. Update CI YAML that invokes the CLI by name:

```bash
find . -type f \( -name "*.yml" -o -name "*.yaml" \) -not -path "*/.git/*" \
  -exec sed -i 's/\bfabric-dataops-toolkits\([[:space:]]\|$\)/sigantry\1/g' {} +
```

A pinned reference such as `fabric-dataops-toolkits==<version>` is left as it is: replace it by hand.

## Verify

```bash
pip install sigantry
sigantry doctor
```

On a release after 1.0.0, or a source install of `main`, also run this from the directory that holds your config file:

```bash
python -W error::DeprecationWarning -W error::UserWarning -c "from sigantry_core import FabricDataOps; FabricDataOps.from_config()"
```

It exits 0 only when no `FDT_` settings override, settings key spelled in another letter case or legacy entry-point group is in use, the legacy config file is not read, alone or beside a different `.sigantry.toml`, no settings variable is ignored, and `from_config()` can build your configuration where you run it. A legacy file beside an identical `.sigantry.toml` passes, because `.sigantry.toml` is the file read; delete the legacy file before you edit `.sigantry.toml`, or from then on the legacy file is read instead. One case prints a warning without failing the command: an unprefixed variable that 1.0.0 read, such as `TENANT_ID` (`FutureWarning`). Otherwise it exits non-zero with the first problem it met: a `DeprecationWarning` that names a legacy name, a `UserWarning` that names a file or variable that is not read, or the error that stopped the build, for example a `KeyError` when the config names a plugin that is not installed there.

The two filters turn every `DeprecationWarning` and `UserWarning` into an error, not only the ones about your settings. One raised by the `from sigantry_core import FabricDataOps` import, or while `from_config()` reads your settings or builds a plugin, fails the command with that warning: read the message. One raised while a plugin's module is imported does not: that plugin is not loaded. The same holds for the notification sinks, secret stores and approval gates that `sigantry` registers itself. If your config does not name that plugin, the command says nothing about it. If it does, building that plugin fails with the `KeyError` above even though the plugin is installed. If you get that `KeyError` for a plugin you have installed, run the command again without the two `-W` options: if the `KeyError` goes away, a warning was raised while the plugin was imported.

On 1.0.0 this command says nothing about your config. 1.0.0 warns about neither old name, and it can exit 0 while ignoring a file you renamed to `.sigantry.toml`. On 1.0.0 the config file is read only if it is named `.fabric-dataops.toml` or you pass its path explicitly, and a settings override is read only if it starts with `FDT_`.
