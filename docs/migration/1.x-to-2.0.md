# Migration: `fabric-dataops` 1.x to `fabric-dataops-toolkits` 2.0 (now a consumer-pattern reference)

> **Status (2026-04-22):** No live `fabric-dataops` v1 consumer exists.
> Cross-repo verification (HANDOFF.md § "Important correction — AIMS
> and DQ") confirmed that AIMS v1.4.4 and DQ Framework v2.0.0 never
> imported `fabric_dataops` at any point. The original framing of
> this file as a v1→v2 migration guide was aspirational. It has been
> re-scoped as a **consumer-pattern reference** for any project
> (greenfield or inherited) adopting `fabric-dataops-toolkits 2.x`.
>
> If you genuinely hold a v1 pin somewhere, the before/after tables
> below still apply — everything after Step 1 is unchanged.

**Audience:** any project consuming `fabric-dataops-toolkits 2.x`
— greenfield, HS2-internal, or external. The examples assume the
HS2 plugin (`fabric-dataops-toolkits-hs2`) for tenant-specific
behaviour; skip those sections if your consumer will author its own
plugin or run against the base-only testing doubles (see
`tests/integration/test_greenfield_hss.py`).

**v2 is a hard break from v1** (which was never adopted): every
import path, every CLI name, every environment variable, and every
template filename changed. The old `fabric-dataops 1.x` distribution
was archived and receives no further releases.

---

## Summary of changes

| Concern                 | 1.x                                                                       | 2.0                                                                                             |
| ----------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Base distribution       | `fabric-dataops`                                                          | `fabric-dataops-toolkits`                                                                       |
| Python import           | `fabric_dataops`                                                          | `fabric_dataops_toolkits`                                                                       |
| HS2 code home           | baked into base                                                           | separate wheel `fabric-dataops-toolkits-hs2`                                                    |
| Auth                    | internal `TokenProvider`                                                  | `AuthProvider` protocol + plugin                                                                |
| Config                  | `HS2_*` env vars                                                          | `.fabric-dataops.toml` + `pydantic-settings` overrides                                          |
| Deploy call             | `from fabric_dataops.deploy.profiles.aims import deploy_aims`             | `FabricDataOps.from_config(".fabric-dataops.toml").deploy(DeployContext(...))`                  |
| DQ call                 | `from fabric_dataops.dq.gate import run_gate`                             | `FabricDataOps(...).run_dq_gate(suite, data_ref)`                                               |
| Telemetry               | hardcoded `Custom-Hs2*` stream names in base                              | owned inside `fabric-dataops-toolkits-hs2/.../log_analytics_sink.py`                            |
| ADO YAML templates      | `hs2-secure-pipeline.yml`, `hs2-spark-diagnostic-emitter.yml`             | `secure-pipeline.yml`, `spark-diagnostic-emitter.yml`                                           |
| PowerShell module       | `Hs2Fabric` 1.x (monolithic)                                              | generic `Fabric` 1.0 + `Hs2Fabric` 2.0 wrapper requiring `Fabric`                               |
| CLI                     | `fabric-dataops`                                                          | `fabric-dataops-toolkits`                                                                       |
| New diagnostic          | -                                                                         | `fabric-dataops-toolkits doctor` lists installed plugins + import errors                        |
| Bicep                   | HS2 defaults hardcoded                                                    | `resourcePrefix`, `tagPrefix`, `runbookBaseUrl`, `alertEmail`, `actionGroupShortName` required  |

## Step 1: Update dependency declarations

**Old `requirements.txt` / `pyproject.toml`:**

```toml
[project.dependencies]
fabric-dataops = ">=1.0,<2"
```

**New:**

```toml
[project.dependencies]
fabric-dataops-toolkits = ">=2.0,<3"
fabric-dataops-toolkits-hs2 = ">=1.0,<2"
```

Install from the ADO Artifacts feed:

```bash
pip install fabric-dataops-toolkits fabric-dataops-toolkits-hs2 \
  --index-url https://pkgs.dev.azure.com/HS2-DataAndAnalytics/COE%20Fabric%20AIMS/_packaging/fabric-dataops-toolkits/pypi/simple/
```

## Step 2: Create `.fabric-dataops.toml` at the repo root

v1.0 consumed a handful of environment variables directly. v2.0 uses a
TOML file plus `pydantic-settings` env-var layering (`FDT_<section>__<key>`
overrides).

**Old (env-var surface — copy from current `.env` / pipeline variables):**

| 1.x env var                   | Purpose                                      |
| ----------------------------- | -------------------------------------------- |
| `HS2_FABRIC_WORKSPACE_ID`     | default workspace target                     |
| `HS2_TELEMETRY_PRINCIPAL`     | stamped on every `TelemetryEvent.properties` |
| `HS2_TELEMETRY_DCE_URI`       | Data Collection Endpoint                     |
| `HS2_TELEMETRY_DCR_ID`        | DCR immutable id                             |
| `HS2_TELEMETRY_STREAM_DEPLOY` | deploy telemetry stream name                 |
| `HS2_TENANT_ID`               | Entra tenant                                 |
| `HS2_RUNBOOK_BASE_URL`        | wiki base URL for alert runbooks             |

**New `.fabric-dataops.toml` at the consumer repo root:**

> `[core].tenant_id` is optional at the base level — a greenfield consumer
> doing telemetry-only does not need one. Plugins that *require* a tenant
> (AuthProvider, AimsDeployProfile) validate it themselves on construction.
> Each named plugin reads its own nested `[<seam>.<name>]` TOML table and
> receives those fields as constructor kwargs, OR consumes the table via an
> optional `from_settings(cls, settings: dict)` classmethod.

```toml
[core]
tenant_id = "<your-tenant-id>"

[auth]
provider = "hs2_entra_group"

[telemetry]
sink = "log_analytics"

[telemetry.log_analytics]
dce_uri = "https://<your-dce>.ingest.monitor.azure.com"
dcr_immutable_id = "<your-dcr-immutable-id>"
stream_name = "Custom-Hs2Deploy"

[deploy]
profile = "aims"

[deploy.aims]
wheel_glob = "dist/*.whl"
items_dir = "./fabric_items"

[dq]
gate = "dq_framework"

[runbooks]
registry = "hs2_teams"

[capacity]
policy = "hs2"
```

Env overrides stay available via pydantic-settings:

```bash
FDT_CORE__TENANT_ID=<tenant>      # overrides [core].tenant_id
FDT_DEPLOY__PROFILE=aims          # overrides [deploy].profile
```

## Step 3: Migrate `deploy` calls

### Old v1.0

```python
from fabric_dataops.deploy.profiles.aims import deploy_aims

result = deploy_aims(
    client,
    workspace_id="...",
    environment_id="...",
    wheel_path="dist/aims_data_platform-1.4.4-py3-none-any.whl",
    items_directory="./fabric_items",
    parameters_path="./parameters.yml",
)
```

### New v2.0

```python
from fabric_dataops_toolkits import FabricDataOps
from fabric_dataops_toolkits.protocols import DeployContext

fdo = FabricDataOps.from_config(".fabric-dataops.toml")
result = fdo.deploy(
    DeployContext(
        workspace_id="...",
        environment="PROD",
        parameters={
            "wheel_path": "dist/aims_data_platform-1.4.4-py3-none-any.whl",
            "environment_id": "...",
            "items_directory": "./fabric_items",
            "parameters_path": "./parameters.yml",
        },
    )
)
```

`result` is a `DeployResult` value object (`workspace_id`,
`items_published`, `items_failed`, `raw`). All HS2 wheel-upload detail
now lives inside `result.raw["aims_wheel"]`.

## Step 4: Migrate `run_gate` calls

### Old v1.0

```python
from fabric_dataops.dq.gate import run_gate

result = run_gate(
    suite_name="silver_checks",
    dataset="abfss://...data@...dfs.core.windows.net/silver/",
    fail_on_violation=True,
    fail_on_empty=True,
)
```

### New v2.0

```python
from fabric_dataops_toolkits import FabricDataOps
from fabric_dataops_toolkits.protocols import DataRef

fdo = FabricDataOps.from_config(".fabric-dataops.toml")
result = fdo.run_dq_gate(
    "silver_checks",
    DataRef(name="silver", path="abfss://...data@...dfs.core.windows.net/silver/"),
)

if not result.success:
    raise SystemExit(
        f"suite={result.suite!r} failed: {result.violations} of "
        f"{result.evaluated} expectations violated (run_id={result.run_id})"
    )
```

Violations and empty-suite handling are no longer booleans on the
signature — the caller inspects `result.success` + `result.violations`
directly.

## Step 5: Migrate telemetry emit calls

### Old v1.0

```python
from fabric_dataops.monitor.emit import emit_event

emit_event("aims_deploy_start", {"workspace": "...", "principal": "..."})
```

### New v2.0

```python
fdo = FabricDataOps.from_config(".fabric-dataops.toml")
fdo.emit("aims_deploy_start", {"workspace": "...", "principal": "..."})
```

The sink is resolved from `[telemetry].sink` in the TOML. Passing
`strict=True` surfaces sink exceptions instead of swallowing them.

## Step 6: Update ADO pipeline template references

### Old v1.0

```yaml
extends:
  template: templates/extends/hs2-secure-pipeline.yml@templates
```

### New v2.0

```yaml
extends:
  template: templates/extends/secure-pipeline.yml@templates
  parameters:
    resourcePrefix: "hs2"
    tagPrefix: "hs2"
    runbookBaseUrl: "https://dev.azure.com/HS2-DataAndAnalytics/COE%20Fabric%20AIMS/_wiki/wikis/AIMS%20Platform%20Docs/runbooks"
    alertEmail: "fabric-alerts@hs2.co.uk"
    actionGroupShortName: "hs2fabric"
```

Sister templates renamed analogously: `hs2-spark-diagnostic-emitter.yml`
→ `spark-diagnostic-emitter.yml`. Consumer pipelines supply the HS2
defaults inline via parameters or from a variable group.

## Step 7: Update PowerShell module pin

### Old `requirements.psd1`

```powershell
@{
    ModuleVersion = '1.2.0'
    RequiredModules = @(
        @{ ModuleName = 'Hs2Fabric'; RequiredVersion = '1.4.0' }
    )
}
```

### New

```powershell
@{
    ModuleVersion = '2.0.0'
    RequiredModules = @(
        @{ ModuleName = 'Fabric';    RequiredVersion = '1.0.0' },
        @{ ModuleName = 'Hs2Fabric'; RequiredVersion = '2.0.0' }
    )
}
```

`Fabric` ships the generic cmdlets (`Get-FabricToken`,
`Get-FabricTenantSetting`). `Hs2Fabric` 2.0 re-exports them with the HS2
tenant defaults stamped in and adds the HS2-specific helpers.

## Step 8: Verify with `fabric-dataops-toolkits doctor`

After installing both wheels, run:

```bash
fabric-dataops-toolkits doctor
# or, for containers / isolated venvs where the console script is not on PATH:
python -m fabric_dataops_toolkits doctor
```

Expect a rich table listing all six HS2 plugins with `ok` status:

```text
                 fabric-dataops-toolkits plugins
  Group              Name             Module                           Version Status
  auth_providers     hs2_entra_group  fabric_dataops_toolkits_hs2....  1.0.0   ok
  capacity_policies  hs2              fabric_dataops_toolkits_hs2....  1.0.0   ok
  deploy_profiles    aims             fabric_dataops_toolkits_hs2....  1.0.0   ok
  dq_gates           dq_framework     fabric_dataops_toolkits_hs2....  1.0.0   ok
  runbook_registries hs2_teams        fabric_dataops_toolkits_hs2....  1.0.0   ok
  telemetry_sinks    log_analytics    fabric_dataops_toolkits_hs2....  1.0.0   ok

  6 plugin(s) discovered across 6 seam group(s).
```

Pass `--strict` in CI to make the command exit non-zero when any plugin
fails to import.

## Cross-repo migration script (for the platform team)

The two consumer repositories (`1_AIMS_LOCAL_2026/` and
`2_DATA_QUALITY_LIBRARY/`) need a coordinated cross-repo PR cycle. Each
repo should:

1. Checkout a feature branch:

   ```bash
   cd /home/sanmi/Documents/HS2/HS2_PROJECTS_2025/1_AIMS_LOCAL_2026
   git checkout -b feature/migrate-to-toolkits-2.0
   ```

2. Apply Step 1 (dependency declarations) in `pyproject.toml` /
   `requirements.txt`.

3. Apply Step 2 (`.fabric-dataops.toml`) at the repo root.

4. Apply Step 3 (`deploy_aims` → `FabricDataOps.deploy`) in every
   deployment entry point (typically `scripts/deploy.py` in AIMS).

5. Apply Step 4 (`run_gate` → `FabricDataOps.run_dq_gate`) where
   applicable (typically `scripts/run_dq.py` in DQ).

6. Apply Step 5 (telemetry) wherever `emit_event` is called.

7. Apply Step 6 (template references) in every `azure-pipelines.yml`
   and `pipelines/*.yml`.

8. Apply Step 7 (PowerShell module pin) in `requirements.psd1` or the
   module manifest consumed by CI.

9. Run the consumer repo's own test suite:

   ```bash
   pytest tests/ -q
   ```

10. Smoke deploy against the HS2 Fabric test tenant and confirm
    equivalent outcome vs pre-migration (same items published, same
    DQ gate result, same telemetry rows).

11. Run `fabric-dataops-toolkits doctor` and paste the output into the
    PR description as proof all plugins load.

12. Open a PR, merge when green, cut a consumer-side release.

Repeat for the DQ Framework consumer.

## Troubleshooting

- **`KeyError: 'aims'`** — the HS2 plugin is not installed. Run
  `pip install fabric-dataops-toolkits-hs2` and re-run
  `fabric-dataops-toolkits doctor` to confirm.

- **`ValidationError` on load** — the TOML is malformed or is missing
  `[core].tenant_id`. The error message names the offending path.

- **`DeployProfile not found` / plugin not listed by doctor** — confirm
  `[deploy].profile` matches a registered entry point (doctor output
  column `Name`). Typos in the TOML surface here.

- **Telemetry emits succeed but rows never appear in Log Analytics** —
  `[telemetry.log_analytics]` DCE URI, DCR immutable id, or stream name
  is wrong. Run `fabric-dataops-toolkits doctor --strict` after
  temporarily setting `fabric_dataops_toolkits_hs2.telemetry.log_analytics_sink`
  log level to `DEBUG` for full diagnostics.

- **CLI reports `command not found`** — the CLI was renamed to
  `fabric-dataops-toolkits`. The old `fabric-dataops` entry-point was
  removed (hard break — no shim).

## Rollback

v2.0 is a hard break. Rollback requires pinning the v1.x packages in
`pyproject.toml`:

```toml
[project.dependencies]
fabric-dataops = ">=1.0,<2"
```

The platform repo's `v1.0.0` tag is preserved for this case. Note that
the v1 package has been archived — no security fixes ship to it.
