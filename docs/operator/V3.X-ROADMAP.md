## Phase 17 — SYNC-PUBLISH (compose `sync apply` + first-time publish) — **SHIPPED**

> **Status: SHIPPED via PR #70** (commit `d6ae92a`, merged 2026-05-02). Live-verified 2026-05-06 against `COE_F_SBDEVOPS_POC` workspace (3 items / 3 folders, idempotent re-run, audit hashes `d233e645…` / `64b45b6f…`). The DoD checklist below is retained for traceability.

- **Source:** ADR-0012 (Accepted 2026-05-01) Option C, deferred. Surfaced by 2026-05-01 brownfield live test against `COE_F_SBDEVOPS_POC` -- the seed notebook had to be deployed via direct REST after `sync apply` returned `items_packaged=1` without publishing.
- **Scope:** Add `sigantry sync apply --with-publish` opt-in flag. When set:
  1. `sync apply` runs as today (folder reconcile + existing-item placement).
  2. After reconcile completes, the engine identifies manifest items whose `(display_name, type)` is absent from the workspace.
  3. For each absent item, drive `fabric_cicd.FabricWorkspace.publish_all_items` against the staging tree's per-item subdir (re-using the packagers' staging artefacts).
  4. Emit a single combined `DeployRecord` with `provider="sync-engine-publish"` and a `published_items` array distinct from `moved_items`.
- **Prerequisites:**
  - `parameters.yml` argument (or inference rule from a sibling file).
  - Composability spec for cases where some items exist + some don't (mixed-state run).
  - SemVer-safe: default behaviour stays as today; flag is purely additive.
- **Falsifiability tests (must ship green):**
  - First-time-deploy of N items via `sync apply --with-publish` results in N items in the workspace + 1 DeployRecord with `published_items.length == N`.
  - Mixed run (M existing items reparented + N new items published) produces a DeployRecord with both arrays populated.
  - `--with-publish` without `--params parameters.yml` errors with a clear message.
  - Failure mid-publish leaves the folder reconcile committed (publish errors don't roll back the folder topology -- separate concerns) but emits a DeployRecord with `outcome="partial-failure"`.
- **DoD:**
  - Flag implemented in `sigantry_core/sync/cli.py` + `sigantry_core/sync/apply.py`.
  - Engine wires fabric-cicd via the existing `sigantry_core/deploy/parameters.py` substitution path (PR #54 work).
  - 4 new unit tests + 1 live integration test (against `COE_F_SBDEVOPS_POC`).
  - `docs/runbooks/sync/apply.md` §1.3 "First-time publish via --with-publish".
  - ADR-0012 amended to mark Option C as Implemented; new ADR captures the chosen `parameters.yml` resolution rule.

## Phase 18 — NOTIFICATION-V2 (replace `sigantry_core/sync/notifications.py` stand-ins)

- **Source:** Phase 16 SEAM-04 shipped a pluggable `NotificationSink` Protocol + entry-point plugin model. The Phase 13 `sigantry_core/sync/notifications.py` Teams / Slack / Email stand-ins were never migrated to the new seam; they remain wired into `sigantry_core/sync/_notify_main.py` selected by `SIGANTRY_NOTIFICATION_SINK` env var.
- **Scope:**
  1. Lift the three concrete stand-ins (`TeamsSink`, `SlackSink`, `EmailSink`) into separate plugin packages OR into `sigantry-core/notifications/` as the SEAM's reference implementation, whichever the Phase 16 SEAM author intended.
  2. Update `_notify_main.py` to resolve sinks via `NotificationSink` registry instead of the hardcoded if/elif on `SIGANTRY_NOTIFICATION_SINK`.
  3. Operator-facing env-var name stays the same (`SIGANTRY_NOTIFICATION_SINK={teams,slack,email,...}`) so existing CI workflow YAMLs don't break.
- **Prerequisites:** Phase 13 Test 6 must close first (operator-bound -- needs a Teams webhook on HS2). Without an end-to-end-proven Teams sink, refactoring it is premature.
- **Falsifiability tests:**
  - `sigantry doctor` shows the three sinks discovered via the SEAM-04 entry-point model (not as hardcoded fallbacks).
  - A stranger plugin author can publish `my-org-pagerduty-sink` via `entry_points = {"sigantry.notification_sinks": ["pagerduty = my_org.pd:PagerDutySink"]}` and `SIGANTRY_NOTIFICATION_SINK=pagerduty` resolves it.
  - Existing `tests/sigantry_core/notifications/test_{teams,slack,email}.py` continue to pass without modification.
- **DoD:**
  - `sigantry_core/sync/notifications.py` deleted (or re-exports for SemVer continuity until v3.x).
  - `sigantry-core/notifications/` (or whichever location the SEAM author specified) holds the reference impls.
  - Phase 13 Test 6 evidence updated to show resolution-via-SEAM, not resolution-via-hardcoded-mapping.

## Candidate — LEGACY-SURFACE-DROP (the residue SHIM-DROP deliberately kept)

- **Source:** v3.1 SHIM-DROP execution (2026-06-11). Three legacy surfaces were
  deliberately retained past the shim window and need a coordinated drop:
  1. **Registry dual-read** of `fabric_dataops_toolkits.<seam>` groups
     (`sigantry_core/registry.py` `_LEGACY_GROUPS` / `_LEGACY_TO_NEW` +
     `_load_legacy_entry_point`). Kept as a grace window for third-party
     plugins; the PR #91 dual-read shadow telemetry exists precisely to prove
     zero legacy-group resolutions before removal. Removing it also retires the
     legacy-group tests in `tests/sigantry_core/test_registry.py`.
  2. **Config-surface rename** — ~~step 1 shipped~~. The loader now resolves
     `.sigantry.toml` by default and the typed-settings env-prefix is
     `SIGANTRY_`; `.fabric-dataops.toml` and `FDT_` are read for one more minor
     release, each emitting a `DeprecationWarning` that names the replacement.
     **Remaining: step 2 — remove both legacy surfaces one minor later**, along
     with the legacy-prefix tests in `tests/sigantry_core/test_config.py` and
     the `FDT_` setenv in `tests/sync/test_cli_sync_preview_warning.py` that
     deliberately pins the legacy path end-to-end.

     Note for step 2 and for anyone extending the loader: the env sweep in
     `_apply_env_overrides` merges only `<PREFIX><SECTION>__<KEY>` forms whose
     `<SECTION>` is a field of `ToolkitSettings`, and **no** model in the tree
     enables pydantic-settings' own env source — the root model drops it, and
     the 13 seam sub-models are plain `BaseModel`, not `BaseSettings`. That
     second half matters as much as the first: while the sub-models were
     `BaseSettings` with no `env_prefix`, each one ran an env source that
     matched *unprefixed* names, so bare `TENANT_ID`, `PROVIDER` and
     `REGISTRY` bound onto settings regardless of what the root model did.
     Do not make a sub-model a `BaseSettings` again. Both are load-bearing under the shared
     `SIGANTRY_` prefix, which it does *not* own: ~70 operational variables
     share it, several of them credentials (`SIGANTRY_SMTP_PASSWORD`,
     `SIGANTRY_GITHUB_TEST_PAT`, `SIGANTRY_FABRIC_TOKEN`). An unfiltered sweep
     binds those onto `ToolkitSettings`, which allows extra fields, and
     `model_dump()` then renders them in clear. Leaving pydantic's env source
     enabled additionally turns the 13 bare `SIGANTRY_<SECTION>` names into
     `SettingsError` crashes. `tests/sigantry_core/test_config.py` pins both.
  3. **In-package `sigantry_core/sync/notifications.py` shim** (Plan 16-01
     Open-Q-1) — the Phase 13 name aliases re-exporting the Phase 16 seam
     impls; `tests/sync/test_notifications.py` pins it.
  Optional rider: the conda env name `fabric-dataops-toolkits`
  (environment.yml / Makefile), which breaks every contributor machine on
  rename — needs an announced cutover window.
- **Falsifiability:** shadow telemetry shows 0 legacy-group hits over an agreed
  observation window; `entry_points(group="fabric_dataops_toolkits.x")`
  resolution removed with tests asserting the legacy groups are no longer read;
  config loader resolves `.sigantry.toml` by default with the legacy filename
  warning-then-failing per the two-step schedule *(step 1 met: resolution and
  the warning ship with tests; step 2 — removal — outstanding)*.

### Candidate — BULK-API-BACKEND (wrap the Bulk Export/Import item-definition APIs)

- **Source:** LANDSCAPE-2026-06 §2.4 + recommendation 3. Microsoft's Bulk Export and
  Import Item Definition APIs (Preview, March 2026) are the closest platform-native
  analog to `sync apply --with-publish`: batch, LRO, SPN-capable, dependency-ordered.
- **Scope (spike first):** evaluate the bulk APIs as an *alternative backend* for the
  sync-publish path — same manifest, same `DeployRecord` audit emission, different
  engine. Revisit the ADR-0012 / ADR-0013 boundary reasoning against them. Do NOT
  replace the fabric-cicd backend; add a seam if the spike validates.
- **Prerequisites:** the APIs leaving Preview (or an explicit decision to depend on
  Preview); live-tenant credentials for an e2e probe.
- **Falsifiability:** a spike notebook/script that round-trips one manifest through
  export -> import on a test workspace, with timings + failure-mode notes committed
  to `.planning/research/`.

### Watch items (no phase until the platform feature stabilises)

- **Branched workspaces / selective branch-out (Preview, FabCon 2026)** natively covers
  the feature-workspace lifecycle. The "feature-workspace auto-create/destroy" idea
  from [docs/RELATED-WORK.md](../RELATED-WORK.md) §2/§4 is **closed as obsoleted** —
  do not build it; document the native feature in the runbooks once it GAs.
- **Fabric MCP servers + microsoft/skills-for-fabric**: automation UX is moving toward
  AI agents driving Fabric APIs. Increases (not decreases) the value of the
  non-pluggable audit plane; candidate future work is an MCP-facing surface that
  exposes Sigantry's audited verbs as MCP tools.
- **New API surfaces with no Sigantry verb** (LANDSCAPE-2026-06 §5): connection-reference
  variables, Outbound Gateway Rules API (API-only when private links are on — natural
  governance-toolkit fit), delegated tenant-setting override CRUD, workspace-level
  surge protection. Each is a small verb-shaped candidate once an operator need shows.
- **Explicit non-goal re-affirmed:** thin CRUD verb expansion. That lane belongs to the
  `fab` CLI (GA, SLA-backed). Per LANDSCAPE-2026-06 recommendation 6.

## How to escalate an item from "candidate" to "committed"

1. The next milestone-open (e.g. `gsd-new-milestone v3.1`) reads this file.
2. The roadmapper agent picks 3-7 phase candidates per milestone based on business pull + dependency constraints.
3. Each chosen phase becomes a `.planning/phases/<N>-<slug>/` tree with PLAN.md, SPEC.md, etc.
4. Items NOT chosen stay here for the milestone after.

The corollary: nothing here is forgotten. Whether v3.1 picks Phase 17 or Phase 18 first (or both), the spec's already half-written.
